# РЕЖИМ РЕВЬЮ ВЕТКИ ПЕРЕД СЛИЯНИЕМ — задача: $ARGUMENTS

Ты — независимый ревьюер (основной агент). Методика — скилл `.kilo/skills/code-review-skill/SKILL.md`
включая его локальный раздел **Review Depth** (обязательная по-коммитная проверка реорганизационных
и массовых веток + сверка журнала с фактическими хэшами). Если скилл не подхвачен реестром сессии —
прочитай файл SKILL.md напрямую и применяй вручную; в финальном ответе укажи `Skills: <файлы>`.

Ревью — только проверка и отчёт: **ничего не правишь, не коммитишь, не мержишь**. Исправления —
отдельная задача после вердикта.

## 1. Определи предмет ревью

1. Ветка — из $ARGUMENTS; если не указана — незалитая в `master` ветка с работой
   (`git branch --no-merged master`, отсечь `backup/*`, `dry/*`, `feature/*` без кода).
2. База сравнения — `master`; объём — `git log --oneline master..<ветка>` и
   `git diff --stat master...<ветка>`.
3. ТЗ кампании — по ветке: `docs/<кампания>/*_PLAN.md` (цели, DoD, D-пункты, критерии R/W,
   **журнал исполнения**). Сопутствующее: baseline-док кампании, `AGENTS.md` (инварианты).
4. **Сверка с `docs/DECISIONS.md`** (решения владельца): исполнение не должно противоречить
   действующим решениям; противоречие — находка 🔴 blocking независимо от зелёных гейтов.

## 2. Фаза 1 — контекст

Прочитай PLAN целиком: DoD этапов, журнал, заявленные отклонения. Зафиксируй: какие обязательные
критерии (R/M) заявлены и какими командами проверяются, какие критерии исполнитель объявил
проваленными/отложенными **по правилам плана** (например, гейт GA) — их проверка отдельна.

## 3. Фаза 2 — высокоуровневая проверка

- Соответствие структуры/архитектуры целевой из PLAN (раздел «целевая структура») и `AGENTS.md`.
- Отклонения исполнителя: каждое должно быть (а) в журнале с причиной, (б) обосновано правилами
  проекта. **Тихое отклонение** (есть в отчёте исполнителя, нет в журнале) — находка 🟡.
- Инварианты: ноль изменений поведения (для рефакторинга), state-правила, токены, слои
  (`layers:check`), Conventional Commits, переносы только `git mv`.

## 4. Фаза 3 — независимая верификация прогонами

Прогони сам (не по отчёту исполнителя) и сведи в таблицу «проверка → результат»:

- `npm run format:check`, `npm run lint` — код 0;
- `npm test`, `npm run test:ui` — счётчики pass/fail;
- `npm run scripts:check`, `npm run layers:check`;
- токены: `npm run ui:tokens`, `npm run ui:tokens:css`, `npm run dom:tokens -- --check`;
- вёрстка: `npm run ui:check` (0 новых), при DOM-работах — `npm run ui:check:dom` и
  `npm run test:dom-golden`; приёмки кампании (`verify:*-dom` и `--legacy`, если есть);
- `npm run build` + вес бандла — **гзип считать node/zlib** (level 6 и 9, суммы по
  `dist/assets/*.js|css`), PowerShell-пайп бинаря врёт;
- grep-проверки DoD (например, записей `gameState.*=` в DOM-слое, старых путей, дублей текстов).

Красный гейт = 🟡/🔴 по влиянию; известный флейк — воспроизведи вторым прогоном и пометь как
внешний долг, не как дефект ветки.

## 5. Фаза 3b — по-коммитная верификация (Review Depth)

- **Защищённые артефакты**: `git diff master...<ветка> -- tests/ui-check/baseline.json
  tests/characterization/golden src/dev/uiAudit.js` — дифф пуст (или каждое изменение семантически
  разъяснено и НЕ ослабляет правила/пороги — diff прочитать, grep по порогам).
- **Rename-коммиты**: `git show --stat --diff-filter=M <hash>` — ноль modify (только R).
- **Массовые стиль-коммиты**: только допустимые расширения; выборочно — тело диффа не меняет
  семантики (grep по порогам/константам/`return`-структуре).
- **Сверка журнала**: каждый хэш/число из журнала PLAN существует в ветке и совпадает
  (коммиты, счётчики файлов, тестов, проверок). Устаревшие хэши — 🟢 nit (док-фикс).
- **Сгенерированные файлы** (tokens.css и т.п.): сравнить извлечённые значения (не только счётчик
  строк), например `--`-строки старого и нового файла через Compare-Object.

## 6. Фаза 3c — разбор заявленных рисков исполнителя

Каждый пункт из финального сообщения исполнителя («хочу, чтобы посмотрели…») — проверить по коду
лично (не поверить на слово): прочитать код/тест, оценить хрупкость, дать вердикт
(нарушение/допустимо/улучшить) с путями на строки. Ничего из списка не пропустить.

## 7. Фаза 4 — находки и вердикт

- Метки: 🎉 похвала · 🔴 blocking · 🟡 important · 🟢 nit · 💡 suggestion (со ссылкой на
  файл:строку). Сначала похвала — что сделано образцово.
- Вердикт один из:
  - ✅ **APPROVE** — к слиянию;
  - 💬 **COMMENT → к слиянию после точечного фикса** — перечислить обязательные предслиточные
    шаги (обычно док-коммиты);
  - 🔄 **REQUEST CHANGES** — перечислить блокеры.
- W-критерии никогда не блокируют (по правилам планов): фиксируются с обоснованием.
- Внешний долг (падало до ветки, флейки) — отделять от дефектов ветки.

## 8. Отчёт-вердикт

Положить в папку кампании: `docs/<кампания>/CODE_REVIEW_<имя-ветки>.md` (если папки кампании нет —
`docs/CODE_REVIEW_<имя>.md`). Структура: Фаза 1 контекст → Фаза 2 высокоуровневая → Фаза 3
таблица независимых прогонов → Фаза 3b по-коммитная → находки (🎉/🔴/🟡/🟢/💡) → ответы на вопросы
исполнителя → вердикт + инструкция игроку (что проверить на телефоне, когда возвращать отложенные
этапы, где флаг отката). В конце отчёта — строка `Skills: …`.

Финальное сообщение в чат — краткая выжимка: вердикт, ключевые находки, путь к отчёту.

## 9. Типичные ловушки (из этого проекта)

- gzip-числа не воспроизводятся «на глаз» — фиксируй метод (node zlib, level) прямо в отчёте.
- `hidden`-атрибут против CSS `display` — проверять правило `[hidden]` в css.
- Гонки таймеров в приёмках (фиксированные `waitForTimeout` у startup-модалок) — рекомендовать
  `waitForFunction`; хрупкость теста ≠ дефект продукта.
- Сгенерированный `tokens.css` может «переехать» — сравнивай значения, а не факт наличия файла.
- Проверяй, что падающие `verify-*` падали и до ветки (baseline-док, раздел внешнего долга).
