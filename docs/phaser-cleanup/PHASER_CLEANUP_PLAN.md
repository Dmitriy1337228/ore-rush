## 10. Аварийные стопы, откат и условия пересмотра

### 10.1. Политика сбоев

1. Красный обязательный критерий внутри этапа: до 2 попыток исправления в рамках плана. Не исправлено → `git revert` коммитов этапа (история не переписывается), запись в журнал.
2. После отката — аварийное завершение: финальный отчёт «план не выполнен» (выполненные этапы, место сбоя, причина, состояние ветки); ветка `chore/phaser-cleanup` остаётся для разбора, **в `master` не сливается**. Частичный результат автоматически не принимается; продолжение — новым запуском игрока.
3. Превышение бюджета этапа > 50 % — запись в журнал, продолжение; **жёсткий стоп — 3 дня** (2–3 дня кода, правка 11): достижение — аварийное завершение по п. 2. Апрув golden и проверка телефона в бюджет не входят.
4. **Нельзя «лечить проверку»:** не ослаблять `UI_RULES`/пороги гейтов, не расширять `tests/ui-check/baseline.json`, не скрывать объекты ради зелёного прогона, не править golden вне одной перезаписи 2.5.

### 10.2. Откат

- Точка восстановления: `backup/pre-phaser-cleanup` + `git bundle ..\game_clicker-pre-phaser-cleanup.bundle` (этап 0.2, по правилу AGENTS.md о бекап-ветках и `git bundle`).
- Откат этапа — `git revert` его коммитов; перезапись истории не предполагается; если когда-либо понадобится — только с предварительной бекап-веткой и `git bundle`, push — `--force-with-lease` и по явному указанию игрока.
- Откат дефектов DOM-форм **после слияния** — `git revert`, не флагом (D0).

### 10.3. Условия пересмотра (из вердикта)

1. Фаза 3 затягивается/не стартует, а владелец хочет закрыть налог двойной поддержки настроек (464 мёртвых строки, скрытая сборка) — вариант architect «C1: настройки сейчас, C2 после G-итога» (с правкой флага до `status`/`upgrades`); правки 4–10 вердикта действуют и для C1. Оформляется отдельным решением владельца — этот план при этом не стартует.
2. G-итог фазы 3: M3 no-go или автооткат M2 — объём сноса пересчитывается (список/статус остаются Phaser), D0 закрывается этим исходом.
3. Владелец явно снимает правило «обновление `golden/ui` только после апрува игрока» — апрув композитов отпадает, перезапись выполняется с сводным осмотром дифа агентом.
4. Этап 0 показывает, что список потребителей/композитов существенно больше (> 20 файлов) — разбить на две волны (после M2 фазы 3 / после M3) отдельным решением.

## 11. Правила исполнителя (кратко)

1. Один этап — один набор коммитов, Conventional Commits (`refactor(ui)|refactor(ui)!|docs(ui)|test(ui)|chore(scripts): …`); тема со строчной буквы, без точки.
2. Бизнес-логика и запись состояния — только `src/state.js`/`src/state/*`; тексты — только модули сообщений; DOM-контроллеры не меняются, кроме как по сносу их Phaser-пар.
3. Любая правка вёрстки (а их в сносе почти нет — только вынос раскладки) — `npm run ui:check:quick` + осмотр размеченных PNG `shots/ui-check/`; минимум два вьюпорта: 1280×720 и 390×844.
4. Токены: голых чисел раскладки не плодить; вынос раскладки — без смены значений (`L.*` из `src/layout.js`).
5. Не трогать: `UI_RULES`, пороги, `baseline.json` (кроме `--update-baseline`), golden вне шага 2.5, `gear.js`, `hud.js`, `tutorial.js`, `mapScreen.js`, `src/game/*`, исторические документы кампаний.
6. Новый/изменённый скрипт — алиас + строка в `scripts/README.md` (`npm run scripts:check`); запуск скриптов — только по алиасам.
7. После каждого этапа — полный набор гейтов П3; отчёт этапа — в журнал.
8. Вопросы игроку — только до старта (невыполненное предусловие) и после финала (апрув, телефон, слияние).
9. Применённые скиллы — в отчёте: `Skills: <файлы>`.
