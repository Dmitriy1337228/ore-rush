## 1. Резюме (TL;DR)

- Пилот доказал: самый тяжёлый форм-экран (мастерская) на DOM даёт **0 нарушений аудита** (было 99), **p95 16.8 мс** против 33.3, прод-бандл **меньше** baseline (406.8 + 2.0 КБ gzip против 412.4), паритет S1–S10 и подтверждение на телефоне.
- Предлагается перенести на DOM **только формы**, продолжая тем же паттерном: снимок `bridge.js`, общие компоненты, токены, `ui:check:dom`, DOM-golden. Игра (шахта, бой, босс, HUD, обучение) остаётся в Phaser.
- Порядок по данным (коммиты/`fix` за 90 дней): **настройки** (10/4) → **пакет статус-модалок** (8/2) → **список улучшений** (8/3) → **карта** (5/2, только с обоснованием).
- Таймбокс фазы: **≤ 5 рабочих дней** чистой работы; каждая форма — отдельный коммит-милестоун с паритет-гейтом и снимком. При провале критериев форма возвращается на Phaser, ветка не разрастается.
- Что **не** делаем: не переносим HUD/бой/босс/шахту/обучение, не трогаем `state.js`/экономику/сейвы, не заявляем «весь UI на DOM».

## 4. Предлагаемый объём фазы

### 4.1. Милестоун M1 — Настройки (0.5–1 день)
- DOM-модалка: статы, тумблеры «Звук/Музыка», слайдер громкости, две кнопки сброса с подтверждением второй.
- Снимок: `settings`-поля из `gameState` (уровни/статы, `soundOn`, `musicOn`, `musicVolume`) + производные строки; тумблеры/слайдер вызывают существующие функции состояния/sfx.
- Гейты: `ui:check:dom` (state `settings-dom` по 7–9 вьюпортам), DOM-golden, ввод/подтверждение, паритет текстов.
- Критерий: 0 нарушений, долг по настройкам снят, `settings`-golden Phaser заменён на DOM-эталон по апруву.

### 4.2. Милестоун M2 — Статус-модалки (0.5–1 день)
- Один каркас `dom/statusModal.js` для 4 форм; данные — снимок (`dailyInfo`, `offlineInfo`, `bossReward`, `playerDown`).
- Очередь и D3 сохраняются: Phaser-оверлеи приоритетнее; DOM-мастерская закрывается/уступает.
- Критерий: 4 сценария (ежедневная, оффлайн, вырубило, награда) — паритет по кнопке/суммам, 0 console, 0 нарушений; снят долг 4 состояний.

### 4.3. Милестоун M3 — Список улучшений (1.5–2 дня)
- Вкладки, ряды (имя, уровень, цена/доход, прогресс, кнопка покупки), мультипокупка, скролл с сохранением позиции; секция снаряжения в бою — за теми же компонентами.
- Снимок расширяется дороже всего: уровни/цены/доступность/дельты; **бизнес-логика покупки остаётся в `state.js`** (`buyBulk`, `canBuy`, `unlockTier`).
- Риск производительности: до ~40 рядов, обновление 150–250 мс; замер p95 обязателен (порог +2 мс).
- Критерий: паритет покупки/вкладок/МАКС/скролла и локов; golden заменяется по апруву.

### 4.4. Карта — решение отдельно
Переносим только если после M1–M3 у карты по-прежнему ≥ 2 `fix`/квартал и удаётся сохранить анимации прибытия/камеру без просадок. Иначе карта остаётся в Phaser (осознанно, с записью в журнал).

### 4.5. Что не входит
HUD, бой, босс, шахта, обучение; баланс/экономика/сейвы; любые редизайны «заодно».

## 5. Технические решения (наследуются от пилота)

### 5.1. Паттерн формы
`src/dom/<form>.js` — контроллер по образцу `craftScreen.js`: `create<Form>(scene)` → `open/close/isOpen/tick/destroy`; структура через `components.js`; данные — только `bridge.js`; действия — только функции `state.js`; тексты — модуль сообщений формы (по образцу `craftMessages.js`).

### 5.2. Раскладка и токены
Размеры — только `var(--*)` из `src/dom/tokens.css`; новые единицы добавляются в `DOM_EXTRA` генератора с обоснованием. Никаких голых `px/rem/em` (гейт `ui:tokens:css`). Ориентация — класс `portrait/landscape` от прямоугольника канваса (как в мастере).

### 5.3. Почему HUD остаётся
- Обновляется каждый кадр/клик; DOM-текст на 60 Гц — это layout/paint поверх канваса, реактивность убирает обвязку, но не стоимость отрисовки.
- В HUD сходятся игровой цикл, эффекты урона и боевые оверлеи — риск и цена ошибки выше, чем у форм.
- Допустим отдельный HUD-спайк (20 Гц + `transform`-бары + замер p95 ≤ baseline+2 мс). Без этого спайка HUD не переносим.

### 5.4. Инфраструктура проверок
1. Обобщить `ui-check-dom`: реестр DOM-форм (`root`, `expectedRows`, состояния) вместо селекторов мастерской.
2. `dom-golden`: параметр формы и каталог `tests/characterization/golden/dom/<form>/`.
3. `ui-matrix`: состояния `<form>-dom`; Phaser-состояние удаляется вместе с кодом формы после апрува.
4. Полный прогон остаётся: `npm run ui:check` + `ui:check:dom` + `test:dom-golden` + `npm test` + `test:ui`.

### 5.5. Переходный период
- Каждая форма переносится отдельным милестоуном: DOM включается флагом `?domForm=settings` **только на время милестоуна**; после апрува игрока флаг становится дефолтом, Phaser-форма удаляется отдельным коммитом.
- Один стек не поддерживаем дольше одного милестоуна; soak — по желанию игрока (пилот показал, что можно без него, но риск признаём).

## 6. Критерии успеха (общие для каждого милестоуна)

Обязательные:
1. **Паритет поведения** — сценарии формы зелёные скриптом (по образцу S1–S10): все кнопки/переключатели/подтверждения.
2. **Ввод** — тапы не проваливаются, скролл не нажимает, дрожание ≤10 CSS px = тап (Playwright).
3. **Размеры** — 0 ошибок `ui:check:dom` на 6–9 вьюпортах, интерактив ≥40 px, текст ≥10 px.
4. **Нет регрессий** — `npm test`, `test:ui`, `ui:tokens`, `ui:tokens:css`, `dom:tokens --check`, `ui:check` без новых нарушений.
5. **Слои** — D3: Phaser-оверлеи не прячутся под DOM-формой; очередь модалок сохраняется.
6. **Тексты/логика** — нет дублей бизнес-правил и сообщений вне `state.js`/модуля сообщений формы.

Желательные:
7. **LOC формы** — DOM-версия (JS+CSS+разметка+тест) ≤ Phaser ×1.3.
8. **Бандл** — прирост на форму ≤ 15 КБ gzip (после удаления Phaser-кода — обычно отрицательный).
9. **p95** — прирост ≤ 2 мс при открытой форме.

Провал любого обязательного — форма откатывается на Phaser, причина в журнал; остальные милестоуны не блокируются.

## 10. Альтернативы

1. **Остаться на Phaser** — продолжить раздел 5 `UI_LAYOUT_TODO` (MIN-FONT, слепые зоны, токены). Дешевле на бумаге, но оставляет причину багов и дорогие правки.
2. **Перенести всё UI на DOM, включая HUD** — отклоняется: частые обновления, боевые слои, риск без доказанного выигрыша; возможен HUD-спайк с замером.
3. **PhaserJSX** — см. пилот 8.3: не решает скролл/тач/переносы; не рассматриваем, пока DOM-путь работает.
4. **Только настройки и статус-модалки, панель оставить** — допустимый «минимум»: 1–2 дня, снимает половину правок, но не трогает самый частый экран (список).
