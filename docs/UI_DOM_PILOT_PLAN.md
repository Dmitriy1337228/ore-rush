# План-ТЗ: пилот «форм-экраны на DOM» (исполняемая версия)

Статус: **УТВЕРЖДЁН игроком, к исполнению** · Дата апрува: 2026-11-16 · Версия 3 (по вердикту /judge от 2026-11-16)
Основа: `docs/UI_DOM_PILOT.md` (предложение, остаётся как обоснование — не править).
Связанные: `docs/UI_LAYOUT.md`, `docs/UI_LAYOUT_TODO.md`, `AGENTS.md` (гейты UI, токены, скиллы).

Что изменено относительно предложения (по вердикту):
1. Сначала **урезанный пилот на фикстурах** (этап 1) — проверяет неизвестное (шрифт, масштаб, слои, DOM-аудит); паритет с `state.js` — только после зелёного гейта G1.
2. **Baseline снимается до разработки** и коммитится отдельно (этап 0).
3. Технология по умолчанию — **vanilla/htm без Vue**; Vue допустим только при условии из D1.
4. В критерии добавлены: слои (Phaser поверх/под DOM), обучение, Yandex-оверлей, CSS-гейт токенов, tolerant-diff для DOM-golden.
5. Тексты ошибок мастерской выносятся из сцены в общий модуль.
6. Бюджет честный: **6–8 рабочих дней**, жёсткий стоп 8.
7. no-go разделён: «DOM хуже» и «оценка не сбылась».
8. Фаза 2 (миграция остальных форм) ограничена заранее и решается отдельным документом.

## 0. Как пользоваться документом

### 0.0. Стартовая инструкция исполнителю (прочитать первой)

1. Прочитай целиком этот документ, затем `AGENTS.md`, `docs/UI_LAYOUT.md`, `.kilo/skills/ui-layout-check/SKILL.md`; если существует `.kilo/skills/INDEX.md` — сверься с ним и прочитай 1–2 релевантных скилла (например, `phaser-scale-and-responsive`, `phaser-input-keyboard-mouse-touch`).
2. Работай в одиночном режиме (команду `/team` не поднимать — игрок не просил).
3. Начни с этапа 0 и иди строго по порядку; следующий этап — только после выполнения всего DoD предыдущего.
4. **Точки остановки (обязательно остановиться и дождаться игрока):**
   - **P1** — после спайка шрифта/рамок (шаг 1.6): нужны скриншоты с реального телефона от игрока. Запроси: «открой `<url dev-сборки>/?dom=1` на телефоне, сделай скриншот мастерской-макета, пришли».
   - **P2** — гейт G1: итог этапа 1 с числами; ждать решения игрока «go/stop».
   - **P3** — гейт G2: приёмка паритета (скриншоты ландшафт/портрет против эталонов).
   - **P4** — этап 4 (4.5): повторная проверка на телефоне.
   - **P5** — гейт G3: итоговая таблица и решение go / no-go-A / no-go-B.
   - Формат остановки: одно сообщение — что сделано, числа, что именно нужно от игрока, список вариантов ответа. Не продолжать работу «в ожидании».
5. Любая неоднозначность, не покрытая планом, — один вопрос игроку (`question`), не домысливание.
6. Отчёт каждого этапа: что сделано, результаты команд DoD (вывод), отклонения, `Skills: <файлы>`, запись в журнал (раздел 12).

- Исполнитель — агент (одиночный режим; командный — только по явному `/team`), приёмщик — игрок.
- Работа идёт строго по этапам. Этап считается закрытым **только когда выполнены все пункты его DoD**. Переход к следующему — после отметки `[x]` в журнале (раздел 12) и коммита.
- Каждая команда в DoD — копируемая и должна завершаться кодом 0 / «0 новых нарушений».
- Любое отклонение от плана — запись в журнал с причиной. Тихие отступления запрещены.
- Нельзя «лечить проверку»: не ослаблять `UI_RULES`, не расширять `tests/ui-check/baseline.json`, не скрывать объекты ради зелёного прогона (правило `AGENTS.md`).

## 3. Этап 1 — Урезанный пилот на фикстурах (2–3 дня) → гейт G1

Цель: за минимальную цену ответить на **дорогие неизвестные**. Бизнес-логика `state.js` не подключается; данные — фикстуры.

### Шаги
- 1.1. **Слой `#ui-root`** (`src/dom/root.js`): контейнер над `canvas`, `position:absolute`, размеры берутся из `getBoundingClientRect` канваса + `ResizeObserver` + событие `resize` `game.scale`; `pointer-events:none`, у панелей — `auto`. Учесть FIT-масштаб, центрирование, DPR.
- 1.2. **Спайк технологии** (≤ 2 часа): один ряд предмета на vanilla-шаблонах и на Preact+htm; сравнить размер, удобство, совместимость с Vite 8. Результат — запись в журнал + выбор по D1.
- 1.3. **Токены в CSS** (`src/dom/tokens.css`, генерация из `theme.js` скриптом `scripts/gen-dom-tokens.mjs`; `npm run dom:tokens`): `--space-*`, `--font-*`, `--hit-*`, `--touch-min`, `--card-*`. Ручные правки сгенерированного файла запрещены; проверка дрейфа `npm run dom:tokens -- --check` (в CI/DoD).
- 1.4. **Три типа рядов на фикстурах:** (а) ряд предмета (иконка в слоте, название, эффект, запас, ошибка, 2 кнопки), (б) ряд рецепта (имя, «Получишь», «Нужно» иконка+число, статус, кнопка с таймером), (в) сетка артефактов (2 колонки ландшафт / 1 колонка портрет). Не менее 12 рядов, чтобы был скролл. Нативный `overflow-y:auto`, `overscroll-behavior:contain`, `touch-action:pan-y`.
- 1.5. **Рамки и текстуры:** `border-image` + `image-rendering:pixelated` для панелей и 3 состояний кнопок; слот иконки — отдельный элемент (без растяжения «запечённого» слота).
- 1.6. **Шрифт:** `@font-face` Monocraft; кегли — только целые CSS px из токенов; проверка рендера в Chrome DevTools с DPR 1, 1.25, 1.5, 2, 3 и **на реальном телефоне** (игрок присылает скриншоты).
- 1.7. **Слои:** проверить D3 на макете — открыть DOM-панель и вызвать любой Phaser-оверлей (дневная награда через DevPanel); зафиксировать наблюдаемый порядок и предложение по правилу.
- 1.8. **Черновой DOM-аудит** `scripts/ui-check-dom.mjs` (Playwright, `getBoundingClientRect`): обход **всех** строк с прокруткой; правила: перекрытие интерактивных/текстовых блоков, выход за границы панели, min тач-зона, min кегль, отступ от рамки. Пороги брать из `UI_RULES` (`src/dev/uiAudit.js`) без ослабления; если для CSS px нужна пересчётная константа — вынести в именованную константу с комментарием.
- 1.9. **Замеры:** p95 кадра с открытой фикстурной мастерской (тем же скриптом, что в baseline), вес бандла, строки кода слоя.

- Возврат к DOM: появятся ≥ N новых форм-экранов в плане продукта; в Phaser-пути повторятся баги тач-зон/скролла.
- Отказ от DOM: Monocraft не даёт приемлемого рендера; DOM-панель мешает эффектам/обучению; Yandex-окружение ломает слой.
- PhaserJSX — отдельный пилот только если DOM отклонён на слоях/шрифте и автор ответит на вопросы про скролл через камеры и hit-зоны с допуском тапа.

## 13. Правила исполнителя (кратко)

1. Один этап — один набор коммитов, Conventional Commits (`feat|fix|docs|test|chore(ui|craft|dom): …`).
2. Любая правка вёрстки сопровождается `npm run ui:check:quick` и осмотром `shots/ui-check/`; перед сдачей этапа — полный набор: `npm test`, `npm run test:ui`, `npm run ui:tokens`, `npm run ui:check` (+ `ui:check:dom`, `ui:tokens:css` после их появления).
3. Минимум два вьюпорта на правку: 1280×720 и 390×844; к апруву — скриншоты и отчёт аудита.
4. Никаких голых чисел раскладки: токены/CSS-переменные; обоснованное исключение — только с комментарием «что и зачем».
5. Бизнес-логика только в `state.js`; тексты ошибок только в `craftMessages`.
6. Не расширять `tests/ui-check/baseline.json`; не ослаблять `UI_RULES`.
7. Не трогать экраны, кроме мастерской (D7).
8. Применённые скиллы указывать в отчёте: `Skills: <файлы>`.
9. Если этап упирается в нерешённый вопрос — остановиться и спросить игрока одним вопросом, не додумывать.
