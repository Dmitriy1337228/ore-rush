# docs/ — индекс документации

Актуально на 2026-11-17. Группировка — по смысловым задачам (кампаниям): у каждой задачи своя папка, где лежат предложение, план, baseline-замеры, ревью и эталонные скриншоты.

Жизненный цикл кампании: агент пишет **предложение** по шаблону `PROPOSAL_TEMPLATE.md` → `/judge` выносит вердикт → из предложения делается `*_PLAN.md` (неделимый, с DoD и журналом) → исполнение с полными гейтами → ревью ветки `CODE_REVIEW_*` → игрок сливает в `master`; baseline и эталонные артефакты остаются в папке кампании.

## Живые документы (в корне docs/)

| Документ | Что это |
|---|---|
| `DECISIONS.md` | **Действующие решения владельца** — обязательны к сверке перед стартом задачи, в `/judge` и `/review` |
| `PROPOSAL_TEMPLATE.md` | Шаблон предложения новой кампании: агент пишет по нему, /judge утверждает, затем делается `_PLAN.md` |
| `UI_LAYOUT.md` | Правила вёрстки UI, гейты, протокол аудита — **действующий** стандарт |
| `UI_LAYOUT_TODO.md` | Остаточный долг вёрстки — обновляется по мере закрытия |

## Папки кампаний

Состав каждой папки: `*.md` (предложение-обоснование, не правится) → `*_PLAN.md` (исполняемая версия: DoD, правила, журнал исполнения) → `*_BASELINE.md` (замеры «до»: гейты, LOC, нарушения, gzip, p95) → `CODE_REVIEW_*.md` (ревью ветки перед слиянием) → `baseline/` (эталонные PNG, если кампания о вёрстке).

`REPO_REFACTOR.md` · `REPO_REFACTOR_PLAN.md` · `REPO_REFACTOR_BASELINE.md` · `CODE_REVIEW_REPO_REORG.md`
Статус: **ВЫПОЛНЕН**, ветка `chore/repo-reorg` слита в `master` 2026-11-17.

### `docs/dom-pilot/` — пилот «мастерская на DOM»
`UI_DOM_PILOT.md` · `UI_DOM_PILOT_PLAN.md` · `UI_DOM_PILOT_BASELINE.md`
Статус: **ВЫПОЛНЕН**, пилот закрыт с G3 = go.
Артефакты (`baseline/`): `craft-*.png` — эталоны мастерской на 6 вьюпортов; `shots.json` — список эталонных прогонов; `pilot-dom/` — апрув-скриншоты DOM-мастерской (ландшафт/портрет).

### `docs/dom-phase2/` — фаза 2 «формы на DOM» (настройки + статус-модалки)
`UI_DOM_PHASE2.md` · `UI_DOM_PHASE2_PLAN.md` · `UI_DOM_PHASE2_BASELINE.md` · `CODE_REVIEW_PHASE2_DOM.md`
Статус: **ВЫПОЛНЕН (частичный go)** — настройки на DOM; отложенный M2 разблокирован решением владельца (см. `DECISIONS.md` №3) и передан в фазу 3.
Артефакты (`baseline/`): `phase2/` — Phaser-эталоны 5 состояний форм на 6 вьюпортах (нужны, когда M2 стартует) + `settings-dom/` (DOM-снимки настроек); `phase2-dom/` — скриншоты DOM-настроек к апруву, 7 вьюпортов.

## Предложения на согласование (ждут /judge) — финальный пакет доработок

| Папка | Предложение | Что закрывает |

| `docs/phaser-cleanup/` | `PHASER_CLEANUP.md` | Снос Phaser-путей форм, флага отката и `--legacy` (после приёмки фазы 3) |

Порядок исполнения: `dom-phase3` → `phaser-cleanup` → `ui-debt` → `code-quality` → `ci`. Каждый предложение содержит D0 «Финальность» (тема закрывается целиком, без «потом») и D-play (участие игрока — только этап 0 и финальная приёмка). После закрытия всех пяти существующие отложенные вопросы исчерпаны.

## Зачем BASELINE-документы

Это зафиксированное состояние «до» начала кампании: выводы всех гейтов, строки кода форм, таблица нарушений по состояниям×вьюпортам, вес бандла, p95 кадра. По ним считаются критерии R/W плана («не хуже baseline»), доказывается «ноль регрессий» и проводится триаж скриптов. После закрытия кампании остаются как история решений и точка сравнения для следующей фазы.
