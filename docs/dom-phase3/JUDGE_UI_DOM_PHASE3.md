### Ответы на вопросы раздела 11 (вердикт по каждому)

**Q1. Порядок M2 → M3 одним планом — ПРИНЯТЬ С ПРАВКАМИ.**
Порядок верен: M2 — готовая дешёвая работа (1–1.5 дня) с готовой заготовкой и завершает D3
(«все модалки — DOM»); M3 — самый частый экран и единственная оставшаяся форма. Правки:
(1) M2 — безусловный, с собственным чекпоинтом (артефакты, скриншоты, телефонный снимок) —
его результат не зависит от M3; (2) M3 — условный милестоун: в этапе 0 короткий спайк/замеры
(≤ 0.5 дня) подтверждают достижимость порога p95 и задержки покупки до вложения 2–3 дней;
(3) сумма таймбокса честная: **3.75–5.25 дня, жёсткий стоп 7 сохраняется** (верхняя граница
собственной арифметики 0.25+1.5+3+0.5 больше «≤ 5» из резюме); превышение — по политике
фазы 2 (запись в журнал, продолжение до стопа).

**Q2. «Снаряжение в бою» — ОТКЛОНИТЬ РЕКОМЕНДАЦИЮ ПРЕДЛОЖЕНИЯ: остаётся постоянным
Phaser-слоём.**
`gear.js` — не вкладка списка, а боевая панель: показывается только при `bossNow && !locked`
и вытесняет список (`UIScene.js:315–321`), покупает и использует расходники посреди боя.
Аргумент «экран списка без него непаритетен» неверен: подмена панели на Phaser-секцию при
скрытом DOM-списке и есть паритет с текущим поведением. Включение означало бы DOM-поверхность
во время боя — граница решения №1 («бой остаётся Phaser»), при том что боевой p95 никогда
не замерялся, риск связки с GameScene оценён самим предложением как «Сред/сред» (§9), а
сигнала к переносу нет (1 чистый fix, baseline §6; дефолт §11 п.5 фазы 2: «оставить в Phaser,
пока не доказано обратное»). В M3 включается только **seam**: при `bossActive` DOM-список
скрывается, Phaser-панель снаряжения показывается; приёмка — старт/конец боя, z-порядок,
отсутствие мигания. ⚠ затрагивает решение №1 — закрыто в сторону №1. В таблице 4.4 строка
«Снаряжение в бою — постоянный Phaser».

**Q3. Карта — ПРИНЯТЬ: постоянный Phaser-слой, с правкой формулировки.**
Карта — игровая сцена с собственной камерой и скроллом (`mapScreen.js`, 570 строк); альтернатива 3
самого предложения признаёт «выигрыш не доказан» (§10.3); сигнала нет (2 чистых fix). D0 требует
закрытия темы. Правки: (1) фиксируется как **классификация слоя** («карта — Phaser-слой» в
`DECISIONS.md` на этапе 0 по ок игрока), а не «форма закрыта навсегда» — отдельное будущее
предложение о редизайне карты не запрещено; (2) согласовать TL;DR §1 с таблицей 4.4 (карта
сейчас не упомянута в перечне Phaser-слоёв резюме).

**Q4. Порог p95 M3 «≤ baseline + 2 мс» — ПРИНЯТЬ С ПРАВКАМИ.**
Порог остаётся **желательным (W)** критерием — W никогда не откатывает форму (§10.2 фазы 2).
Правки: (1) число фиксируется на этапе 0 сразу после замера Phaser-пути и записывается в
baseline-док фазы 3 — сейчас порог принимается вслепую (baseline списка не существует,
§4.1.5 предложения); (2) протокол замера расширен: полный каталог (27 рядов — сверить с
тестом каталога), stress-сид, покой + скролл + серия покупок x100/МАКС + смена вкладок,
CPU×4, 1280×720 и портрет; (3) доп-критерий: «клик → ряд перерисован ≤ 1 кадра» (принудительное
перечитывание снимка ряда после вызова state-функции); (4) отслеживание long tasks > 50 мс;
(5) если замеренный baseline окажется < ~10 мс, «+2 мс» превращается в ловушку — порог
пересчитывается по правилу «меньшее изменение, гейты сохранены» и фиксируется числом до
старта M3.

### Обязательные правки для плана (условия утверждения)

1. **Gear (Q2):** снаряжение в бою — постоянный Phaser; из M3 исключено, оставлен seam
   `bossActive` + его приёмка; строка 4.4 — «постоянный Phaser».
2. **Этап 0 дополнить:** (а) LOC/нарушений-baseline для `upgrades.js` и `gear.js` (в baseline
   фазы 2 их нет — W1 не с чем сравнивать); (б) сверка числа рядов с каталогом (27, 20+7)
   и фиксация в плане; (в) замер p95 Phaser-списка по расширенному протоколу Q4 + фиксация
   порога числом.
3. **Спайк/go-no-go M3** (≤ 0.5 дня, stress-сид, полный игровой цикл): подтверждает p95 и
   задержку покупки до начала 2–3 дней; no-go = «список — постоянный Phaser», D0 закрыт этим
   исходом, M2 не страдает.
4. **D3 расширить за пределы модалок:** DOM-список — постоянная панель, а не модалка; описать
   взаимодействие с обучением (`tutorial.js:49–54,149` привязан к `tabBtns`, учебные слои
   рисует отдельная камера над `listCam`) и с Phaser-оверлеями (dim, кольцо, стрелка): либо
   шаги обучения привязываются к DOM-прямоугольникам, либо список на время обучения остаётся
   на Phaser — выбрать по правилу «меньшее изменение», решение и причина в журнал.
5. **Фасад D6 для списка:** описать контракт (`refreshRows`/`refreshTabs`/`switchTab`/
   `applyPanelVisibility`/`updateBlockLock`); потребители сохраняют ожидания без смены:
   `verify-bulkbuy.cjs` (`sc.rows`), `verify-responsive/rebalance/map/boss` (`ui.rows`,
   `gearRows`), `ui-review.mjs`; флаг отката знает `upgrades` (D5).
6. **Двойной стек:** на DOM-пути Phaser-список не строится/не обновляется (иначе W3 меряет
   двойную работу; прецедент — Phaser-модалка настроек, продолжавшая строиться скрытой,
   журнал фазы 2, этап 2); состав покупки (`buyBulk` + `saveGame` + sfx + tween,
   `upgrades.js:~380–396`) сохраняется через state-функцию или фасад — иначе теряется
   автосейв после покупки (нарушение R1/D2).
7. **«Оптимистичное обновление» → принудительное перечитывание:** после синхронного вызова
   state-функции ряд перерисовывается из результата вызова (без локального пересчёта — МАКС
   знает только `getBulkCost/buyBulk`, `src/state/upgrades.js:113–157`); риск «расхождение
   с state.js» из §9 снимается механикой, а не надеждой.
8. **D0 и G-итог:** строки таблицы 4.4 пишутся **по фактическому G-итогу**; при автооткате
   M3 по R — строка «список улучшений — постоянный Phaser», итоговая строка в `DECISIONS.md`
   «классификация слоёв закрыта» вносится с этим исходом. Финальность D0 не нарушается.
9. **Сценарии:** `verify-status-dom` (SM1–SM9/Q1–Q5) после M3 покрывает «список как слой
   под модалкой» (статус-окно поверх DOM-панели — Q3/Q4 фазы 2); `verify-upgrades-dom` —
   сценарии §4.3 предложения + seam боя; методика `waitForFunction`, не сны.
10. **Телефон:** риск поднят до «Сред/сред»; чекпоинты каждого M — автономные снимки
    `dom-*-phone.html`; финальная приёмка — ручная проверка 375/390 (скролл, вкладки,
    bulk-кнопки) — прецедент p375 фазы 2 показал, что снимки нативный ввод не ловят.
11. **Справочно:** §2.2 «самый правимый файл» неточна (у `upgrades.js` 2 чистых fix против
    3 у `settingsModal.js`, baseline §6); на гейтинг не влияет (№2 отменяет пороги), в план
    формулировку не переносить.

**Обоснование отклонения (почему отвергнутые варианты не подходят именно здесь).**
- *Только M2 (альтернатива 1):* снимает меньше половины вёрсточных правок (§2.2), самый
  частый экран остаётся источником багов и ломает порядок кампаний `docs/README.md` —
  `phaser-cleanup` идёт следом, и без фазы 3 сносить у списка будет нечего. Оставлен как
  резерв при отказе владельца от правок 1–3.
- *Переносить всё сразу без приёмки форм (альтернатива 2):* теряется паритет-контроль
  R1–R8/golden, проверенный фазой 2; приёмка форм — единственный механизм, который поймал
  коллизию `.dom-actions` и клиппинг портрета без участия игрока.
- *Карта в объём фазы (альтернатива 3):* игровая сцена с камерой/анимациями, выигрыш не
  доказан (само предложение, §10.3); 2–3 дня M3 уже на пределе бюджета.
- *Разбить на две кампании (3a/3b):* дублирует этап 0, замеры и ревью (+0.5–1 день) и меняет
  зафиксированный порядок пяти финальных кампаний; резерв только при отклонении правок.
- *Gear в M3 (рекомендация предложения):* см. Q2 — граница решения №1, немереный боевой p95,
  несоизмеримая цена автоотката всего M3 из-за секции из трёх карточек.

**Условия пересмотра.**
1. Владелец явным решением требует gear на DOM и/или бюджет «строго ≤ 5» без принятия верхней
   границы 5.25 → предложение разбивается: M2 отдельным планом (он готов), M3 — отдельный план
   после замера baseline списка.
2. Спайк этапа 0 показывает p95 выше зафиксированного порога на stress-сиде или задержку
   покупки > 1 кадра → no-go M3: список остаётся постоянным Phaser, D0 закрывается этим
   исходом, M2 продолжается.
3. Обучение нельзя привязать к DOM-списку без переноса части обучения на DOM → это нарушение
   №1; вариант «список остаётся Phaser» (см. п. 2) становится предпочтительным.
4. Замеренный baseline списка < ~10 мс → порог «+2 мс» пересчитывается до старта M3 (правка
   Q4), иначе он фиктивен и вытолкнет в виртуализацию за пределы бюджета.
