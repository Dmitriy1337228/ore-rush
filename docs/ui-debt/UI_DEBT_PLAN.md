> ## ⚠ Режим исполнения (обязательно к прочтению)
>
> 1. **План один и неделим по составу и порядку** (вердикт, вариант B): этап 0 → M3 → M1 → M4 → финал; M2 — условный (см. правило этапа 0). Это осознанная правка вердикта, а не отступление: апрувить кадры, которых ещё нет, невозможно.
> 2. **Точка остановки ≠ пауза «как получится»:** ожидание игрока фиксируется в журнале (даты старта/возобновления); календарное ожидание в рабочий бюджет агента не входит, но сдвигает календарь. > 3. **Сбой = аварийное завершение, а не пауза:** красный обязательный критерий, не исправленный за 2 попытки → `git revert` коммитов этапа → финальный отчёт «план не выполнен», ветка не сливается (раздел 12).
> 4. **Предусловие старта (проверяется один раз):** кампании `docs/dom-phase3/` (M2 статус-модалок + M3 списка улучшений на DOM) и `docs/phaser-cleanup/` (снос Phaser-путей форм и флага) **выполнены и слиты игроком в `master`** — порядок кампаний из `docs/README.md` (`dom-phase3` → `phaser-cleanup` → `ui-debt`). Если нет — план **не начинается**, игроку задаётся один вопрос сразу. Основание: DECISIONS №3 — состояния форм, живущие на откатных Phaser-путях, уходят при сносе; сжигать их долг здесь = выброшенная работа.

## 1. Как пользоваться документом

### 1.1. Стартовая инструкция исполнителю

1. Прочитай целиком этот документ, затем `AGENTS.md`, `docs/UI_LAYOUT.md`, `docs/UI_LAYOUT_TODO.md`, `.kilo/skills/ui-layout-check/SKILL.md`; сверься с `.kilo/skills/INDEX.md` (если есть) и при прямом совпадении прочитай 1–2 релевантных скилла.
2. Работай в одиночном режиме (команду `/team` не поднимать).
3. Проверь предусловие старта (блок «Режим исполнения», п. 4). Не выполнено — один вопрос игроку сразу, план не начинается.
4. Иди по этапам в порядке: этап 0 → **точка остановки №1** → M3 → M1 (внутри — **точка остановки №2** на апрувы) → M2 (по правилу этапа 0) → M4 → финал. Следующий блок — после полного DoD предыдущего и записи в журнал (раздел 13).
5. Отчёт каждого этапа: что сделано, выводы команд DoD, отклонения, `Skills: <файлы>` (если применялись) — запись в журнал. Промежуточных сообщений игроку вне точек остановки нет.
6. Развилка, не покрытая планом, — по таблице автоматических решений (раздел 6); нет подходящего правила — вариант с меньшим изменением кода и сохранением гейтов, решение и причина в журнал.

### 1.2. Обозначения

| Обозн. | Значение |
|---|---|
| **DoD** | Definition of Done — проверяемые критерии готовности этапа |
| **Срез** | Пачка правок M1 по одному экрану/слою на выбранных вьюпортах («вьюпорт × экран») |
| **`accepted.json`** | `tests/ui-check/accepted.json` — реестр принятого владельцем долга (вне `baseline.json`) |
| **Ратчет** | Число принятых позиций только убывает; рост блокирует прогон; исчезнувшее из прогонов удаляется автоматически |
| **Report-only** | Режим правила/покрытия: нарушения считаются и печатаются отдельным счётчиком, но не валят прогон и не пишутся в baseline |
| **Строгий режим** | Покрытие/правило считает нарушения полноправными: новые валят прогон |
| **Точка остановки** | Момент, когда план ждёт явного ок владельца (этап 0, апрувы M1) |

### 1.3. Политика сбоев (аварийное завершение вместо паузы)

1. Красный обязательный критерий внутри этапа: до 2 попыток исправления в рамках правил плана. Не исправлено → `git revert` коммитов этапа (история не переписывается), запись в журнал.
2. После отката — аварийное завершение: отчёт «план не выполнен» (выполненные этапы, место сбоя, причина), ветка `debt/ui-debt` остаётся для разбора, в `master` не сливается.
3. Превышение бюджета этапа > 50 % — запись в журнал, работа продолжается; **жёсткий стоп 6 дней** — аварийное завершение по п. 2 **плюс правило исхода** (раздел 8): непрожжённое не закрывается тихо — либо оформляется кандидатом на принятый долг на отдельное ок владельца, либо остаётся обычным долгом в baseline; тема долга в этом случае **не закрывается**, правило R6 «блокер слияния» не вносится.
4. Сбой инфраструктуры гейтов (не вёрстки) — «внешний долг»: записать в журнал, не чинить, критерий — «не хуже baseline».

## 12. Риски, меры, откат

| Риск | В/В | Мера |
|---|---|---|
| Срезы меняют вид экранов → массовая замена golden | Выс/выс | Замены только по протоколу «старый/новый кадр» в точке остановки №2; нетронутый golden — байт-в-байт; отказ → `accepted.json`, не тихая замена |
| Расширение аудита даёт гору новых нарушений | Сред/выс | Порядок D4 (сжигание до усиления порогов); новые нарушения — счётчики, правятся в этом же плане; в baseline не пишутся |
| Спайк контраста не даёт стабильного измерения на Phaser | Сред/сред | Заранее разрешённый исход — warn + счётчик (D3); повторных обязательств до успеха нет |
| `accepted.json` конфликтует с `--update-baseline`/ратчетом | Низк/выс | Unit-тесты R8 (не читает/не пишет; ратчет); запись — только вручную по ок владельца |
| Скрытые ряды тормозят аудит | Сред/сред | Замер W2; кэш построенных рядов в `ui-check` |
| Пачки hit-зон меняют поведение ввода | Низк/выс | `test:ui` + `verify-*` (тап/свайп) после каждой пачки; правило вложенности зон не меняется |
| Предусловие (фазы 3/снос) сорвано или частично | Сред/выс | План не стартует (один вопрос владельцу); частичный снос — ячейки «уходит со сносом» вне лимита M1 |
| Жёсткий стоп 6 | Низк/выс | Правило исхода раздела 1.3 п. 3: без тихого закрытия темы |

**Откат:** любой обязательный критерий, не закрытый за 2 попытки, → `git revert` коммитов этапа → аварийный отчёт; ветка `debt/ui-debt` в `master` не сливается сама — слияние только игроком после финальной приёмки.

## 15. Правила исполнителя (кратко)

1. Один этап — один набор коммитов, Conventional Commits (`fix(balance)`, `feat(audit)`, `docs(ui)`, `test(audit)`…); в коммитах `--update-baseline` — число уменьшения долга.
2. Любая правка вёрстки — минимум **два вьюпорта: 1280×720 и 390×844** + целевой вьюпорт среза; `ui:check:quick` и осмотр размеченных PNG из `shots/ui-check/` обязательны; перед сдачей этапа — полный набор гейтов.
3. Числа раскладки — только `layout.js`/токены с комментариями-обоснованиями (`ui:tokens`); новых «голых» чисел не плодить.
4. Не расширять `tests/ui-check/baseline.json`, не ослаблять `UI_RULES`/пороги, не прятать объекты; долг только сжигается (или уходит в `accepted.json` по ок владельца в пределах лимита).
5. `accepted.json` — записи только вручную, по явному ок владельца на конкретную позицию + строка в `DECISIONS.md`; лимит и ратчет соблюдаются автоматически.
6. Golden обновляется только по покадровому протоколу «старый/новый кадр» (`test:ui`); baseline — не механизм апрува картинки (D7).
7. Бизнес-правила — только `src/state.js`/`src/state/*`; слои — по `layers:check`; `src/ui/dom` не импортирует Phaser.
8. Новый скрипт — в целевую папку (`gates|verify|metrics`), алиас в `package.json` + строка в `scripts/README.md` (`scripts:check`).
9. Новый/изменённый код проходит `format:check`, `lint`, `scripts:check`, `layers:check`; полные UI-прогоны — `ui:check` + `ui:check:dom`.
10. Применённые скиллы — в отчёте этапа: `Skills: <файлы>`.
11. Вопросы игроку — только в точках остановки №1/№2 и финальной приёмке; в середине этапа — аварийный стоп с отчётом, не «продолжить как получится».
